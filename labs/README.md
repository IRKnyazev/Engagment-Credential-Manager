# cm lab walkthroughs

Three mock Active Directory engagements that show how to drive **`cm`** through
real attack flows. They're modelled on well-known training ranges —
[GOAD (Game of Active Directory)](https://github.com/Orange-Cyberdefense/GOAD)
and the [HackSmarter](https://hacksmarter.io) AD series — but every host, hash
and password here is **invented for teaching**. Nothing is a real credential.

Each step shows the *offensive* command for context, then the **`cm`** command
that records the result, with the tool's real output (these walkthroughs were
generated by actually running `cm`, not by hand-waving).

| Lab | Range style | What it teaches in `cm` |
|---|---|---|
| [01 — The North](01-goad-north-single-domain.md) | GOAD, single domain (`north.sevenkingdoms.local`) | enumerated users with no secret, AS-REP/Kerberoast hashes, `export hashes` crack hints, `cracked --from` potfile, `works`/`fail` lockout-safe spraying, `samdump` SAM + NTDS import, `where --valid`, `export pairs` for pass-the-hash |
| [02 — Crossing the Narrow Sea](02-goad-forest-trusts.md) | GOAD, forest & trusts (3 domains) | multiple domains in one DB, forged **kerberos_ticket** blob with expiry, machine accounts, **`supersede`** on a rotated password, crack propagation, per-domain review |
| [03 — Arasaka](03-hacksmarter-arasaka-assumed-breach.md) | HackSmarter-style assumed breach | **`reset`** (ACL abuse / introduced creds), `export pairs --introduced` remediation report, **`merge`** (same box by hostname vs IP), **PFX blob + `unlock`** passphrase, `nxc` import, local-vs-domain realms |

## The one rule that ties it together

`cm` records **only what you actually know**, and fills the gaps later:

- Know *who* but not their secret → `cm add user '<ident>'` (an identity, no secret).
- Know a *secret* but not whose → `cm add secret --pass '<pw>'` (a loose secret).
- Know *both* → `cm cred '<ident>' --pass/--nt/--hash …`.
- Proved a login works / fails → `cm works` / `cm fail` (this is what "untested → valid/invalid" means; recording a cred alone never asserts a login).

## Identity grammar cheat-sheet (used throughout)

| You type | Realm it means |
|---|---|
| `north.sevenkingdoms.local\jon.snow` | **domain** account |
| `sql_svc@castelblack` | **host-local** account |
| `sa@braavos:1433` | account in a **service** (host:port) |
| `--null` | SMB null session (empty username) |

A host can carry **both** an IP and a name: `cm import nxc` links the two it sees
on each line automatically, and you can declare it yourself with
`cm add host NAME --alias IP`, so referencing a box by IP in one place and by name
in another still lands on one host (Lab 03). `merge` is for the case aliases
*don't* fix — the same account filed under two realms (domain vs local).

> Run these against a throwaway DB, e.g. `export CM_DB=/tmp/lab.db` — don't point
> them at a real engagement.
